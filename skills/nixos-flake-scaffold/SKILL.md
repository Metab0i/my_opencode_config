## How to Use This Skill

This skill scaffolds a **reproducible Nix dev environment** around a project using **flakes**. Two parts cooperate:

1. **You (the agent)** supply the intelligence and flexibility: inspect the target project, decide what toolchain and dev tools it needs, confirm exact nixpkgs attribute names, then drive the scaffolder.
2. **`scaffold.py`** is a thin, language-agnostic file-writer. It performs NO project inspection and ships NO built-in package maps. It emits a devShell-only `flake.nix`, a `.gitignore`, and an optional `.envrc`, with a package list **you** fill via repeated `--package <attr>` flags (empty by default).

**Workflow at a glance:** detect the host → gate on nix capability → inspect the project & pick toolchain → confirm package attrs → run `scaffold.py` with `--package` flags → `git add -A` → `nix flake lock` → `nix develop` to verify.

Do not memorize the Nix/flake ecosystem. Fetch the documentation URLs in the **Documentation Reference Index** for exact option names, package attributes, and command behavior when you need specifics.

## Core Concepts

- **Flake**: a directory with a `flake.nix` describing `inputs` (pinned dependencies) and `outputs` (what the flake provides). Reproducible and lockable via `flake.lock`.
- **devShell**: a development environment defined as a flake output (`devShells.<system>.default`), entered with `nix develop`. It is the flakes-era replacement for `nix-shell`/`shell.nix`.
- **`flake.nix` structure**: top-level attributes `description`, `inputs`, `outputs` (a function of the realized inputs), and optional `nixConfig`. This skill's scaffolder emits a devShell-only flake.
- **`flake.lock`**: pins exact input revisions. Generated by `nix flake lock`; updated with `nix flake update`.
- **Flakes feature flag**: flakes are still "experimental". They must be enabled (`nix-command flakes`) before any `nix flake` command works. See **Enabling flakes** below.
- **Flakes + git**: in a git repository, flake evaluation only sees files tracked by git. New files must be `git add`-ed before `nix` can read them, or you'll get confusing "file not found" errors.
- **Systems**: flakes require outputs per system. The scaffolder emits a `forAllSystems` helper so one `devShells` block fans out to every system in `--systems` (default `x86_64-linux,aarch64-linux,x86_64-darwin,aarch64-darwin`).

## The Scaffolding Workflow (agent-driven)

This is the heart of the skill. Follow these steps in order.

### 1. Detect the host

Run the detector (read-only; prints JSON, exits 0 if nix is installed):

```
python3 ~/.config/opencode/skills/nixos-flake-scaffold/scripts/scaffold.py --detect
```

It reports:

```json
{
  "nix":       { "installed": true, "version": "2.24.7", "path": "/run/current-system/sw/bin/nix" },
  "flakes_enabled": true,
  "is_nixos": true,
  "current_system": "x86_64-linux"
}
```

- `nix.installed` true means this host is nix-capable (covers NixOS, standalone Nix, nix-darwin, and the Determinate installer — all of which supply `nix`).
- `current_system` is derived from `uname` (no nix call needed) and is a good default if you want to narrow `--systems` to just the host's system.

### 2. Gate

- If `nix.installed` is **false**: the host is not nix-capable. Do **not** generate any flake files. Fall back to the project language's native scaffolder (`cargo init`, `npm init -y`, `uv init`, `go mod init <module>`, etc.), tell the user flake scaffolding was skipped, and stop. (`scaffold.py` will also refuse to run and print this guidance.)
- If `nix.installed` is true but `flakes_enabled` is **false**: enable flakes first (see **Enabling flakes** below) before proceeding, or prefix every nix command with `--extra-experimental-features 'nix-command flakes'`.

### 3. Inspect the project & decide the toolchain

This is where your judgment lives. The scaffolder will not do this for you.

- **If the target dir already has project files**, identify the language/framework from tell-tale files:
  - `package.json` → Node/JS (toolchain e.g. `nodejs`, maybe `pnpm`/`yarn`/`bun`, dev tools e.g. `pretttier`, `eslint_d`, `typescript`)
  - `Cargo.toml` → Rust (`rustToolchain` or `rustc`+`cargo`, dev tools `rustfmt`, `clippy`, `rust-analyzer`)
  - `pyproject.toml` / `requirements*.txt` / `setup.py` → Python (`python3`, possibly `uv`, `poetry`, `ruff`, `ruff-lsp`, `basedpyright`)
  - `go.mod` → Go (`go`, dev tools `gopls`, `gotools`, `delve`)
  - `*.c`/`*.h`/`CMakeLists.txt`/`Makefile` → C/C++ (`gcc` or `clang`, `gnumake`, `cmake`, `gdb`)
  - other → ask the user or pick a sensible generic set (`git`, `gnumake`).
- **If the target dir is empty and the user wants a *new* project**: choose the language/framework the user asked for, then run the language's **native** scaffolder yourself (`cargo init`, `npm init -y`, `uv init`, `go mod init <module>`, etc.) to create the source skeleton, *then* generate the flake around it. The scaffolder does not run any native init — **you** do, via the Bash tool.
- Decide which **dev tools** (formatters, linters, LSPs) belong in the devShell alongside the toolchain.

### 4. Confirm exact package attributes (do not guess)

Nixpkgs attribute names are exact and surprising. Before passing `--package`, confirm each attr actually exists by searching https://search.nixos.org/packages or by fetching it with webfetch. Examples ofAttrs that bite: `python3` (not `python`), `nodejs`/`nodejs_22` (versioned), `rustToolchain` is rarely what you want — `rustc`/`cargo` are common; specialized setups use flakes like `rust-overlay` or `crane` (fetch the doc index). When unsure, search and verify.

If the project needs something uncommon that the script can't express (overlays, extra flake inputs like `flake-utils`/`flake-parts`/`devshell`, build outputs beyond `devShell`), generate the basic devShell scaffold with `scaffold.py`, then **edit the resulting `flake.nix` by hand** to extend it. Fetch the relevant flake library docs from the index as needed.

### 5. Scaffold

Generate the files. Pass the project name, a description, repeatable `--package` attrs, and `--direnv` if the user wants automatic shell switching:

```
python3 ~/.config/opencode/skills/nixos-flake-scaffold/scripts/scaffold.py \
  --dir <PROJECT_DIR> \
  --name "<PROJECT_NAME>" \
  --description "<one-line description>" \
  --package <attr1> --package <attr2> ... \
  --direnv
```

Use `--dry-run` first to preview the generated files without writing anything. Add `--force` to overwrite an existing `flake.nix` (without it, the script refuses and exits 1 — safer for projects that already have a flake you should examine).

### 6. Required follow-up steps (run these yourself)

The scaffolder writes files only and prints these commands. **You** run them:

```
cd <PROJECT_DIR>
git add -A          # CRITICAL: flakes only see git-tracked files
nix flake lock      # generate flake.lock from inputs (fetches nixpkgs)
nix develop         # enter the devShell to verify it builds
```

If `git` is not initialized yet, `git init` first. If `flakes_enabled` was false, either enable flakes (see below) or prefix the commands with `--extra-experimental-features 'nix-command flakes'`. Confirm the devShell builds and the shellHook fires. If it fails, read the error (usually a misspelled package attr — re-verify on search.nixos.org), fix the `flake.nix`, `git add -A` again, and re-run `nix develop`.

## `scaffold.py --detect` Reference

```
python3 ~>/.config/opencode/skills/nixos-flake-scaffold/scripts/scaffold.py --detect
```

- Output: one JSON object (see step 1) on stdout.
- Exit code: `0` if `nix` is installed, `1` otherwise.
- Detection signals used:
  - nix present: `which nix` + `nix --version`
  - NixOS: `/etc/NIXOS` sentinel, `nixos-version` on PATH, or `/etc/os-release` `ID=nixos`
  - flakes enabled: `nix flake --help` succeeds
  - current system: `uname` machine/sysname mapped to Nix system strings

## `scaffold.py` Codegen Reference

```
python3 ~<...>/scaffold.py [--detect] [codegen options]
```

| flag | default | description |
|---|---|---|
| `--detect` | off | probe host, print JSON, exit (mutually exclusive with codegen) |
| `--dir DIR` | `.` | target directory |
| `--name NAME` | dir basename | project name (sanitized to `[A-Za-z0-9_ .+-]`) |
| `--description DESC` | `Developer shell for <name>` | flake `description` string |
| `--package ATTR` | *(none)* | nixpkgs attr to add to the devShell; **repeatable**; validated as a plausible attr path |
| `--ref REF` | `nixos-unstable` | nixpkgs ref/branch for `inputs.nixpkgs.url` |
| `--systems LIST` | `x86_64-linux,aarch64-linux,x86_64-darwin,aarch64-darwin` | comma-separated Nix systems |
| `--direnv` | off | also write a `.envrc` (`use flake`; requires nix-direnv) |
| `--force` | off | overwrite existing files |
| `--dry-run` | off | print the files that would be written; write nothing |

Behavior:

- Refuses overwrite without `--force` (exit 1). Inspect existing flakes by hand instead of clobbering.
- If nix is not installed, exits non-zero with a "use the native scaffolder" message.
- Creates `--dir` if it does not exist.
- Writes `flake.nix`, `.gitignore` (`result`, `result-*`, `.direnv/`), and (with `--direnv`) `.envrc` (`use flake`).
- Prints the follow-up commands (`git add -A`, `nix flake lock`, `nix develop`); runs none of them.

## Files Written

`flake.nix` (default, empty `packages`):

```nix
{
  description = "Developer shell for <name>";

  inputs.nixpkgs.url = "github:NixOS/nixpkgs?ref=nixos-unstable";

  outputs = { self, nixpkgs }:
    let
      systems = ["x86_64-linux" "aarch64-linux" "x86_64-darwin" "aarch64-darwin"];
      forAllSystems = f: builtins.listToAttrs (map (s: { name = s; value = f s; }) systems);
    in
    {
      devShells = forAllSystems (system:
        let pkgs = nixpkgs.legacyPackages.${system}; in
        {
          default = pkgs.mkShell {
            packages = [ ];
            shellHook = ''
              echo "Welcome to the <name> devShell"
            '';
          };
        });
    };
}
```

With `--package nodejs --package python3`, the `packages` line becomes `packages = with pkgs; [ nodejs python3 ];`.

`.gitignore`:
```
result
result-*
.direnv/
```

`.envrc` (only with `--direnv`):
```
use flake
```

## Enabling Flakes

If `--detect` reports `flakes_enabled: false`, enable flakes before locking. Pick the host-appropriate method:

- **NixOS** — add to the system configuration and rebuild:
  ```nix
  nix.settings.experimental-features = [ "nix-command" "flakes" ];
  ```
- **Home Manager** — same option in the Home Manager config.
- **Standalone Nix** — add to `~/.config/nix/nix.conf` or `/etc/nix/nix.conf`:
  ```
  experimental-features = nix-command flakes
  ```
- **Any host (temporary)** — prefix each command: `nix --extra-experimental-features 'nix-command flakes' flake lock`, etc.

## When the Project Needs More Than a devShell

`scaffold.py` intentionally emits a **devShell-only**, **single-input** (`nixpkgs`) flake. Many real projects need more. In that case, generate the basic scaffold, then edit `flake.nix` by hand and fetch the relevant docs:

- **Avoid the systems boilerplate**: add `flake-parts` or `flake-utils` as extra inputs (https://wiki.nixos.org/wiki/Flake_Parts, https://wiki.nixos.org/wiki/Flake_Utils).
- **Polished dev shells**: add the `devshell` flake (per-TTY prompts, extras, commands).
- **Language build tooling**: fetch language-specific guides — e.g. Rust via `rust-overlay`/`crane`, Python via `poetry2nix` or `uv2nix`, Node via `buildNpmPackage`/`treefmt-nix`, Go via `gomod2nix`. Start from the Nixpkgs manual in the doc index.
- **Actually packaging/building the project**: add a `packages.<system>.default` (or `nixosConfigurations`) output. See the flake output schema doc.

## When the Project Already Has a Flake

Do **not** run `scaffold.py` with `--force` blindly. Read the existing `flake.nix`, understand what it already provides, and edit it to extend the devShell's `packages` (or add a devShell) instead of regenerating. Use `git diff` to review your edits before `nix flake lock`.

## Critical Gotchas

- **Flakes are a feature flag**: any `nix flake`/`nix develop` command fails with "experimental Nix feature" unless flakes are enabled. The detector reports this; enable as above.
- **Flakes only see git-tracked files**: in a git repo, `nix` copies only files that are `git add`-ed to the store. A freshly-scaffolded `flake.nix` must be `git add -A`-ed before `nix flake lock`, or you'll get "file not found"/empty-tree errors. This is the #1 cause of broken fresh scaffolds.
- **No secrets in `flake.nix`**: flake contents are copied to the world-readable Nix store. Use a secret-management scheme (sops-nix, agenix, etc.) for any secrets.
- **Attribute names are exact**: `python3` not `python`, `nodejs_22` not `nodejs22`. Always verify on search.nixos.org before passing `--package`.
- **`builtins.currentSystem` is impure**: the scaffolder's `forAllSystems` avoids it on purpose — it iterates an explicit `systems` list. Don't "simplify" it to `builtins.currentSystem` or evaluation breaks under pure mode.
- **Don't clobber existing flakes**: the script refuses overwrite without `--force` precisely so you read the existing flake first. Respect that — extend, don't regenerate.
- **The scaffolder is language-agnostic by design**: it will NOT detect your language or pick toolchains for you. That decision is yours (step 3). Confirm attrs (step 4), pass them via `--package`.
- **`flake.lock` is binary-history-sensitive**: commit it so collaborators/CIs get the same inputs. Don't `.gitignore` it (the generated `.gitignore` does not ignore it).
- **Mixed-input version skew**: if you later add extra flake inputs, pin them to the same nixpkgs with `inputs.<name>.inputs.nixpkgs.follows = "nixpkgs"` to avoid duplicate nixpkgs versions.

## When the User Needs More

- For packaging/building (not just a dev shell): read the Nixpkgs manual's language builders and the flake output schema, then add a `packages`/`apps`/`nixosConfigurations` output by hand.
- For a system configuration rather than a project: see the existing `nixos-consultant` skill and https://wiki.nixos.org/wiki/NixOS_system_configuration#Defining_NixOS_as_a_flake.
- For non-nix hosts: this skill defers to the language's native scaffolder; no flake files are written.
